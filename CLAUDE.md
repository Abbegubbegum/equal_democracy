# Equal Democracy (Jämlik Demokrati) — Project Reference

## Working Principles (read first)

These override the default Claude Code defaults for this project:

1. **Production-ready by default.** Every change must work on the deploy target (Vercel serverless), not just on a dev machine. No filesystem writes to `public/`, no assumptions of persistent in-process state across requests, no reliance on a long-running Node process. If a feature needs a cron/queue/blob store in production, wire it up — don't leave a dev-only shim. See [SCALING.md](SCALING.md) for the running list of patterns to avoid and the measured headroom on each.

2. **Runtime matters.** Consider what happens after deploy: function cold starts, 60s/300s timeouts, read-only filesystem outside `/tmp`, ephemeral `/tmp`, multiple lambda instances, MongoDB connection pooling, CDN caching of `public/`. A solution that works at 5 users but fails at 500 is not finished.

3. **No legacy.** This codebase has no backwards-compatibility burden. If a name is misleading, rename it. If code is dead or unused, delete it. If a pattern is outdated, rewrite it. Don't add deprecation shims, don't preserve old export names, don't keep "removed for X" comments.

4. **Fix what you find.** If you encounter broken, stale, or low-quality code while working on a different task, fix it in the same change. Don't tip-toe around it or file a follow-up note. The exception is large refactors that would obscure the primary diff — flag those before starting.

5. **Keep this file accurate.** When you add a model, route, page, package, or architectural decision, update the relevant section before completing the task. When you delete something, remove its entry. Stale docs are worse than no docs.

6. **Always Read before Edit.** Before any batch of Edits, Read every target file in the same parallel batch — even just `limit: 1` is enough to satisfy the tool. Don't rely on having read the file earlier in the session, and never assume a renamed/moved path is cached. Firing Edit on an unread path errors out and forces a re-read round-trip, which wastes a turn.

## Maintenance

**Deferred major upgrades (reviewed 2026-08-21).** Everything same-major is current. These were consciously left alone and are _not_ drift: **Next 15.5 → 16.3** + React 19.1 → 19.2 (Pages Router still supported; note `eslint-config-next` is already 16.x), **Mongoose 8 → 9 / mongodb 6 → 7**, **Expo SDK 54 → 57** (RN 0.81 → 0.87 — needs a fresh EAS build _and_ a store release to reach devices), **TypeScript 5.9 → 7** (the Go rewrite), **ESLint 8/9 → 10**, and `@anthropic-ai/sdk` 0.69 → 0.120. Deferred until the Swish integration is live, so a regression in either is not mistaken for the other. Anything in `apps/mobile` that `pnpm outdated` flags at version ~57 is SDK-pinned, not stale — move it with `expo install --fix`, never by hand.

**Store submissions and privacy disclosures** are in [docs/app-store-privacy-disclosure.md](docs/app-store-privacy-disclosure.md) — the data inventory behind Apple's App Privacy answers and Google Play's Data safety form, derived from the schema. `apps/web/public/robots.txt` disallows the admin surfaces, `/api/`, `/radera` and `/login`; `public/sitemap.xml` lists the public pages.

**BankID login, anonymous browsing and the account-model rework** (planned, not yet built) are in [docs/bankid-login-plan.md](docs/bankid-login-plan.md) — the ID-växling constraint that shapes it, the three-state capability model replacing "is there a session?", the account merge, and the release sequencing against installed app builds. Vote signing itself is unchanged and stays documented in [docs/bankid-integration-plan.md](docs/bankid-integration-plan.md).

**Swish payments** are documented in [docs/swish-integration-plan.md](docs/swish-integration-plan.md) (design decisions, findings, and the App Store in-app-purchase exposure in §9b) and [docs/swish-go-live-checklist.md](docs/swish-go-live-checklist.md) (the production switch, step by step).

**Vercel needs `ENABLE_EXPERIMENTAL_COREPACK=1`.** Vercel's build image does not support pnpm 11 — its own table stops at pnpm 10, and it infers the package manager from `pnpm-lock.yaml` (lockfileVersion 9.0, which pnpm 9/10/11 all share), so it logs `Detected pnpm-lock.yaml version 9 generated by pnpm@10.x with package.json#packageManager pnpm@11.21.0` and would otherwise install with pnpm 10 — which does not understand the `allowBuilds` key in `pnpm-workspace.yaml`. With the Corepack variable set, Vercel honours `packageManager` and the log reads `Done in 16.8s using pnpm v11.21.0`. Verify that line after any package-manager change. The project's Vercel Node version is 24.x, comfortably above pnpm 11's 22.13 floor.

**Serverless functions must stay in `arn1` (Stockholm).** `apps/web/vercel.json` pins `"regions": ["arn1"]`. Without that key Vercel defaults to `iad1` (Washington DC) while the Atlas cluster sits in Europe (~16 ms RTT from Sweden), so every database round trip crossed the Atlantic twice — `X-Vercel-Id` read `arn1::iad1::…`, meaning the request hit the Stockholm edge and was then shipped to Virginia. That alone put `/api/mobile/questions` and `/api/mobile/citizen-proposals` at ~1.3 s each in production: ~280 ms of pure routing (measured on a 401, which returns before `connectDB()`), plus a cold Mongo handshake of 6–8 transatlantic round trips, plus one crossing per query wave. The payloads were never the problem — prod holds 47 questions and 147 votes. If you ever move the Atlas cluster, move this region with it; the two must stay co-located.

**Before changing anything that runs per-request or fans out to many recipients**, read [SCALING.md](SCALING.md) — it records where the app stops working as it grows, the measured headroom on each limit, and which ones are knowingly deferred. It also carries the serverless rules that already caused incidents: no filesystem writes outside `/tmp`, no state on `global`, no N+1 query loops (that one exhausted the Atlas connection pool in production).

## Project Overview

A democratic participation platform for Swedish municipalities. Citizens can vote in sessions, participate in budget allocation, submit citizen proposals (medborgarförslag), and engage with municipal council meetings. Built as a Turborepo monorepo.

**Live stack:** Next.js 15 · MongoDB/Mongoose · NextAuth (email OTP) · Pusher (real-time) · Resend (email) · Twilio (SMS) · Anthropic Claude API (PDF extraction) · Tailwind CSS v4 · D3.js · Expo React Native

### Key Patterns

**Auth:** Uses JWT tokens (not NextAuth cookies). Tokens stored via `lib/storage.ts` (expo-secure-store). `useAuth()` exposes `user`, `isLoading`, `requestCode(email)`, `login(email, code)`, `logout()`.

**API calls:** Use `apiClient<T>(path, options)` from `lib/api.ts`. It reads the access token from storage, attaches `Authorization: Bearer`, and silently refreshes on 401 before retrying once.

**Storage:** Use `lib/storage.ts` (`getItem`/`setItem`/`deleteItem`) — a thin async wrapper over `expo-secure-store`. The app is native-only (no Expo web target).

**Navigation:** `(app)/_layout.tsx` composes `@react-navigation/material-top-tabs` via `withLayoutContext` from expo-router, configured with `tabBarPosition="bottom"` and a custom `<BottomBar />` (`tabBar` prop) that renders all four registered tabs (Hem, Rösta, Förslag, Info) with the existing icon/label/active-tint design — there's no hidden/filtered tab in this navigator (`archive` and `sessions` are standalone pushed routes at `app/archive.tsx` and `app/sessions.tsx`, outside the `(app)` tab group entirely, reachable via `router.push` rather than the tab bar). The underlying `react-native-pager-view` gives native, content-tracking horizontal swipe between tabs — drag with finger and the screen content slides under you, snap is velocity-aware. Tabs do NOT wrap around (stops at Hem and Info, matching standard mobile app behavior). Don't switch back to expo-router's `<Tabs>` — under SDK 54 + Expo Go new architecture, that variant's bottom-tab bar fails to render at all on Android emulators.

**Why custom `<BottomBar />` instead of the default top-tabs bar:** The default material-top-tabs bar is a horizontal scrollable strip with an animated indicator under the active label — wrong shape for a bottom nav. The custom component renders state-driven `<TouchableOpacity>` tabs reading `state.routes` / `state.index` / `descriptors[].options.title` from props, plus an icon mapping in `TAB_ICONS`. Tap handler emits a `tabPress` event (so pager-view can react), then calls `navigation.navigate(route.name)` only if not focused. To hide a tab from the bar without removing the screen, filter it by `route.name` in the `BottomBar` render — do NOT use `tabBarButton: () => null` (that's a bottom-tabs option that doesn't exist on `MaterialTopTabNavigationOptions` and will cause a type error).

**Navigation guards:** `(auth)/_layout.tsx` redirects logged-in users to the app. `(app)/_layout.tsx` redirects unauthenticated users to login. Both check `useAuth()`.

**Sessioner screen (app/sessions.tsx) — preserved, not a tab:** Originally the "Sessioner" tab, built for live/real-time brainstorming use (e.g. naming the party). Replaced in the bottom tab bar by the personalized question-selection view (now part of the **Hem** tab — see below) but the screen and its code are kept intact — per explicit decision, it may be needed again for a future brainstorming round — moved to `app/sessions.tsx` (standalone pushed route, same pattern as `archive.tsx`) with its own auth guard, not currently linked from any UI. Vertical pager: uses `react-native-pager-view` with `orientation="vertical"`. Each session is its own page; the page owns its own background `<Image>` (`StyleSheet.absoluteFill`) so there's no shared double-buffer crossfade and no scroll-driven sync to go out of alignment. Inside each page, a `ScrollView` with `nestedScrollEnabled` holds the compact title block + inline proposals list — the user can fine-scroll comments/proposals freely, and pager-view takes over the gesture only when the inner ScrollView is at its top/bottom edge, snapping to the previous/next session. Velocity is handled by pager-view's native gesture recognizer (a flick at the edge commits to next; a slow nudge stays put). The hero block is compact (`paddingTop: insets.top + 64` to clear the MAJ button) and the proposals overlay starts immediately below the title. A subtle chevron-down icon (`scrollAffordance`) fades in at the bottom of the page when `contentHeight > viewportHeight` and disappears once the user starts scrolling. `Image.prefetch()` still warms the cache for all session images on load.

**Sessioner infinite loop (PagerView variant):** Triple-array `[...sessions, ...sessions, ...sessions]` with `initialPage = sessions.length` (first item of middle copy). On `onPageSelected`, if `position < n` or `position >= n * 2` (outer thirds), silently `pagerRef.current?.setPageWithoutAnimation()` to the matching slot in the middle copy. An `isJumpingRef` guards against the silent jump re-triggering `onPageSelected`. This is the pager-view adaptation of the ScrollView-based triple-array pattern still used in `proposals.tsx` — `vote.tsx` no longer uses a carousel (it's a single-question view now).

**Hem screen (index.tsx):** Instagram-like vertical feed of all unvoted active `Question`s. Dark (`#111`) background. On focus, reads `lib/questions-cache.ts` (paints cached data immediately, revalidates behind it) and filters to `s.isActive && !s.userVote` — already-voted questions are hidden. It also subscribes to `onQuestionsChange`, so a vote cast on Rösta drops that question from the feed with no refetch. The feed is a **`FlatList`**, not a `ScrollView`: every card is a full-bleed remote image, and rendering all ~30 at once mounted every `<Image>` upfront and started one blob download per active question simultaneously. Windowing (`initialNumToRender={2}`, `maxToRenderPerBatch={3}`, `windowSize={5}`, `removeClippedSubviews`) is what makes images load as cards come into view. Deliberately **no `getItemLayout`** — its offsets are measured from the start of the content and would have to account for `ListHeaderComponent`; nothing here uses `scrollToIndex` (the back-to-top card calls `scrollToOffset`), so measured layout is both correct and sufficient. Card spacing is `marginBottom` on the card rather than a container `gap`, since a gap sits outside the row a list measures. Each card is a fixed-height (`CARD_HEIGHT = screenWidth × 0.78`) full-bleed image (or solid blue if no image) with a dark tint overlay + bottom dark panel showing the question text and an amber "Välj"-button. Tapping "Välj" calls `selectQuestion(id)` (`lib/selected-question.ts`) and navigates to the Rösta tab via `navigation.navigate("vote")`. Empty state when all active questions are voted: "Du är à jour!" with remaining quota count. No category pills, no gear icon, no star badge — the screen is intentionally clean so horizontal swipe is exclusively the tab bar's gesture.

**VotingQuestionCard (lib/VotingQuestionCard.tsx):** Shared component extracted from `vote.tsx` so the interactive Ja/Nej card (date line, question, two radio alternatives with result bars once voted, vote button / "voted" badge) renders identically on both **Rösta** and **Hem**. Its `VotingSession` prop type mirrors the `GET /api/mobile/questions` response shape directly (`id`, `text`, `imageUrl`, `isActive`, `deadline?`, `createdAt`, `voteCounts`, `userVote`, `categories?`) — no field-name translation happens at the fetch call sites. Takes `session`, `selected`, `onSelect`, `onVote`, `submitting`, `onUnselect` as props — callers own the vote-submission logic (opening `BankIdVoteSheet`, which starts a signing order) and local `selected` state. The card's last row is an "Ångra val" (icon `close-circle-outline`) / "Välj en annan fråga" (icon `refresh-outline`, once voted) button that calls `onUnselect` — this replaced the old debate-launcher button now that the debate lives inline on the page instead of behind a button (see `VotingDebateSection` below).

**VotingDebateSection (lib/VotingDebateSection.tsx):** För/emot debate for a `Question`, rendered as an ordinary inline card directly on the Rösta page (not a modal) — the mobile equivalent of the web's standard-session debate UI in `apps/web/pages/session/[id].tsx`, but keyed by `questionId` instead of `proposalId` (Questions have no `Proposal`; `QuestionComment` is its own model for this reason — see the Database Schema section). Self-contained: fetches `GET /api/mobile/questions/comments?questionId=` on mount (re-fetches if `questionId` changes, since the component stays mounted across question switches) and renders comments directly into the page's own scroll rather than a nested scrollable list. Header reads "Debatt", and the composer (type pills + "Argumentera här" input + send button) is rendered directly under it, _above_ the comment list — otherwise the keyboard covers the input while typing, since the section can sit low on the page. Comments are sorted by rating descending (highest average first) — the server already returns them rating-sorted, and the client re-applies the same sort after optimistic inserts/rating updates so a brand-new (unrated) comment or a freshly-rated one doesn't visibly disagree with that order. Each comment shows a type-colored dot (för=green, emot=red, neutral=gray), text, and a 1-5 star rating (same visual pattern as the `ProposalCard`'s `starsRow` used elsewhere in the app, e.g. the preserved Sessioner screen's `app/sessions.tsx` — and, like all rating UI in this app, a positive-only scale with no downvote) posted to `POST /api/mobile/questions/comments/rate`. Posting a new comment first calls `POST /api/mobile/moderate` (a thin Bearer-auth wrapper around the same `moderateContent()` used by the web's `/api/moderate` — see the Content moderation note below for the nonsense-detection addition) — on `"ok"` it posts immediately; on `"warn"`/`"flag"` it shows an inline MAJ-branded confirm card (yellow/red, "Publicera ändå"/"Avbryt", flag adds a legal-responsibility line) mirroring the web dialog at `session/[id].tsx`. Fails open (posts directly) if the moderation call itself errors. Posting awards `addStars(1)`. When `canPost` is `false` (question not `status: "active"`) the composer and rating taps are hidden/disabled — comments remain visible read-only.

**Rösta screen (vote.tsx):** Single-question view for the question the user chose on Hem — or the one a tapped push notification deep-linked to (see Notification deep links above). On focus reads `getSelectedQuestion()` then `lib/questions-cache.ts` — Hem fetched the identical payload on its way here, so the cached copy paints instantly and the revalidation runs behind the rendered screen instead of behind a full-screen `LoadingLoop`. A failed revalidation never blanks out good cached data (`fetchError` is only set when there is no cache at all). After a successful vote it calls `applyVoteToCache()` so Hem's feed and quota update without a round trip. If nothing is stored (or the ID isn't in the fetched list) shows a blue empty state with a "Välj en fråga på Hem-fliken" button (`navigation.navigate("index")`). If a question is found, renders its image (or solid blue) as a full-screen background + a single `ScrollView` containing `VotingQuestionCard` (vote) followed by `VotingDebateSection` (debate) — the debate deliberately comes after the vote, always visible, no button needed to reveal it. The scroll's `paddingTop` is generous (`insets.top + 260`) so the background image's top edge is visible above the card instead of the card sitting flush under the fixed header. `handleUnselect` (passed to the card as `onUnselect`) calls `clearSelectedQuestion()` and navigates back to Hem. The screen also subscribes to `onSelectedQuestionChange` so a deep link that arrives while Rösta is already focused reloads it. After a vote, shows `CelebrationModal` (+1 star via `addStars(1)`). There is no "suggest a question" entry point on this screen — that lightweight flow was removed; see the Förslag screen note below for the one remaining "submit your own idea" button.

**MAJ assistant (XAIModal.tsx):** Branded as "MAJ" in all user-facing text (rebranded from "XAI"; the file name, the `/api/mobile/xai` route, and the internal `role: "xai"` message-type identifier are unchanged — only display strings and the system prompt changed). A dark-blue circle with a sparkles icon floats at the top-left corner of every tab except Hem (rendered in `(app)/_layout.tsx` as an absolute overlay, z-index 100). Tapping it opens a bottom-sheet chat with the Claude API via `/api/mobile/xai`. Shows context-aware quick-action chips based on the current tab (different prompts for Hem, Rösta, Förslag, Arkiv) plus two common actions (write a comment, submit a proposal). Has a "Anmäl MAJ" flag button (top-right of the sheet) that users can tap to report bad AI output. Uses `claude-haiku-4-5-20251001` with a 300-token limit for quick, concise replies. The floating button hides itself while the modal is open to avoid double-tap confusion.

**Forced/soft update prompts:** The app asks `GET /api/mobile/app-version?version=&platform=` on cold start and on every foreground (throttled to 5 min) and renders whatever verdict it gets — `ok`, `update-available` (dismissable sheet, remembered per offered version) or `update-required` (undismissable wall). Everything that decides the outcome lives on the server (`apps/web/lib/app-version.ts`), including the store links and the Swedish copy, because a build already installed on a phone can only be reached by a web deploy. `LATEST_MOBILE_VERSION` drives the soft nudge — **bump it only once the release is actually live in both stores**, not when EAS submits it, or users get nagged about a version the store doesn't have yet (`pnpm release` prints this reminder after submit). `MIN_SUPPORTED_MOBILE_VERSION` is the hard block, currently the no-op floor `1.0.0`; raise it only in the same change that deletes or breaks a `/api/mobile/*` route older builds depend on — the exact situation the 2026-07 restructure created, where installed builds hit hard 404s with no way to tell the user why. Both are overridable per Vercel environment via `MOBILE_LATEST_VERSION` / `MOBILE_MIN_SUPPORTED_VERSION` (ignored unless they parse as `X.Y.Z`). The endpoint is deliberately **unauthenticated** — the builds most in need of the message are the ones whose auth may already be broken — and CDN-cached for 5 min, so a foreground costs no lambda.

**Notification deep links (tap → the exact new question):** `notifyNewVotingQuestion(questionId, text, tokens)` puts `data: { screen: "vote", questionId }` on the push. In `(app)/_layout.tsx` the tap is handled by `Notifications.useLastNotificationResponse()` — **not** `addNotificationResponseReceivedListener`, because the hook also replays the response the app was _launched_ with, so a cold start still deep-links even though the layout mounts long after the tap (after the session is restored from SecureStore, and after sign-in if the user was logged out). The handler `await selectQuestion(questionId)` first, then `router.navigate(NOTIFICATION_ROUTES[screen])`, then `Notifications.clearLastNotificationResponse()` so a later remount (logout → login) can't replay a stale tap. Because the question is preselected, **Rösta** opens straight on it instead of its "välj en fråga på Hem" empty state — there is no scroll-to-item logic anywhere, the deep link removes the need to find the card in the Hem feed at all. The listener-set half of `selected-question.ts` exists for the one case navigation alone doesn't cover: if the app is already sitting on Rösta when the notification is tapped, the screen never blurs, so `useFocusEffect` won't re-run and `vote.tsx` would keep rendering the previous question — it subscribes via `onSelectedQuestionChange` and reloads when the id actually changes. In real EAS builds the guards flip off and pushes register automatically. `vote.tsx` calls `setBadgeCountAsync(0)` on focus to clear the badge (a local-only API that works in both Expo Go and EAS builds). The FCM V1 service-account JSON for Android is uploaded to EAS project Credentials (Android → FCM V1), so push **delivery** to Android works; the APNs `.p8` for iOS is still pending. `google-services.json` lives at `apps/mobile/google-services.json` and is referenced via `android.googleServicesFile` in `app.json`; its embedded `AIzaSy…` value is the Firebase Android **client** API key (ships inside the APK, safe to commit — GitHub secret-scanning flags the pattern but it's low-severity; restrict it in GCP Console → APIs & Services → Credentials by package `se.vallentunaframat.app` + SHA-1). The real secret is the separate `…firebase-adminsdk….json` service-account key used for FCM V1 — never commit it; it lives only in EAS.

**EAS builds need an explicit Node version (pnpm 11 gotcha).** EAS build workers default to Node 20, but this repo pins `pnpm@11.21.0`, which requires Node >= 22.13 and calls `node:sqlite` — a module that does not exist in Node 20. Every EAS build therefore died in the _Install dependencies_ phase with `ERR_UNKNOWN_BUILTIN_MODULE: No such built-in module: node:sqlite`, on both platforms, from the moment the repo moved to pnpm 11. Fixed by a `base` profile in `eas.json` carrying `"node": "22.23.2"`, which every other profile `extends`. If you bump `packageManager`, check its Node floor against that value.

**EAS production builds:** Package name / bundle id `se.vallentunaframat.app`, owner `vallentuna-framat`. Production AAB is built and released to Google Play Console under internal testing. iOS is live too: the Apple Developer account is active and version 1.0.0 is public in the App Store (App Store Connect App ID `6781031191`). Build numbers bump automatically — `eas.json`'s `production` profile has `appVersionSource: "remote"` + `autoIncrement`, so `versionCode` (android) and `buildNumber` (ios) increment on each build. Manual build command: `npx eas-cli build --profile production --platform android` (or `ios`/`all`) from `apps/mobile`. **Submission is automated for both stores:** Android via a Google Play service-account key (`eas-submit@vallentuna-framat.iam.gserviceaccount.com`) already stored on EAS's servers (not in this repo), releasing straight to the `internal` track — so `submit.production.android` in `eas.json` needs no config; iOS via `submit.production.ios.ascAppId` (`6781031191`). Prefer `pnpm release` (below) over the raw commands — it also handles the version bump, the `android/` cleanup, and auto-submit.

**Cutting a release (`pnpm release`):** `apps/mobile/scripts/release.mjs` (run via `pnpm release [patch|minor|major|X.Y.Z] [--platform android|ios|all] [--no-submit] [--dry-run]` from `apps/mobile`) automates the whole store-push flow. In order: it **refuses to run on a dirty working tree or an empty `## [Unreleased]` section in `CHANGELOG.md`** (all preflight checks run before the first file is written, so a rejected run never leaves a half-bumped tree); bumps the user-facing `expo.version` in `app.json` (semver, defaults to a patch bump) **and mirrors it into the root, `apps/web` and `apps/mobile` `package.json` versions** so one number is true everywhere; rolls `[Unreleased]` into `## [X.Y.Z] - <today>`, opens a fresh `[Unreleased]`, and re-points the compare links; commits `chore(release): X.Y.Z` and tags `vX.Y.Z` (local — push with `git push --follow-tags`); deletes the generated `android/` folder (so EAS prebuilds pristine — see the EAS caveat above), then runs `eas-cli build --profile production --platform <platform> --auto-submit`. **Default platform is `all`** — it builds and auto-submits both stores (Google Play + App Store Connect) in one command; pass `--platform android`/`ios` to do one. It deliberately does NOT touch `versionCode` (android) or `buildNumber` (ios) — `eas.json` has `appVersionSource: "remote"` + `production.autoIncrement`, so EAS bumps both internal build numbers itself. iOS auto-submit needs `submit.production.ios.ascAppId` in `eas.json` — set to `6781031191` (the App Store Connect App ID / numeric "Apple ID" of the app record, not the bundle id); Android submit needs no `eas.json` config (the stored service-account key handles it — see above). Release notes are still written by hand per language after submit — EAS Submit has no changelog support: Google Play Console → "Vad är nytt" (sv-SE), App Store Connect → "What's New in This Version". Drafts live in [docs/release-notes.md](docs/release-notes.md) — note Google Play caps that field at 500 characters, and check which versions actually reached the public store before writing incremental notes (1.2.2 never did). **Store notes and the CHANGELOG are different documents**: `docs/release-notes.md` is user-facing store copy in Swedish, [CHANGELOG.md](CHANGELOG.md) is the developer-facing history the script rolls automatically. The commit and tag happen **before** the build, because EAS uploads the working directory and the build should come from exactly what the tag points at; if the build then fails, the script prints how to either re-run the build or undo the release (`git tag -d` + `git reset --hard HEAD~1`). Dep-free Node launcher, same `spawn(..., { shell: true })` Windows pattern as `start-live.mjs`. Android submit runs unattended via the stored key; iOS submit may prompt for Apple sign-in on the first run per machine, then EAS caches it.

**EAS dev-client builds (push + native testing):** Push notifications and any other native-module feature can't be exercised in Expo Go — build a custom dev client via EAS. `eas.json` has a `development` profile (`developmentClient: true`, `distribution: internal`, APK) and `expo-dev-client` is a dependency. Build from `apps/mobile`: `npx eas-cli build --profile development --platform android`; install with `npx eas-cli build:run --platform android --latest`; then run Metro with `npx expo start --dev-client`. **Local Android native builds (`expo run:android` / `gradlew`) are NOT viable on this machine** — the repo's long OneDrive path + pnpm's deep `.pnpm/<hash>` nesting + New-Arch Fabric codegen (CMake mirrors the absolute source path into each object path) push generated paths past Windows' 260-char `MAX_PATH`, and the JBR JVM / NDK ninja don't honor long paths. Always use EAS for native builds. Caveat: `android/` is gitignored but EAS **still bundles the local `apps/mobile/android/` folder** and prebuilds non-destructively, so stray edits in the generated `android/` (e.g. a `buildDir` relocation) leak into the cloud build and cause baffling Kotlin `Unresolved reference` failures — delete `apps/mobile/android` before an EAS build so prebuild regenerates it pristine.

**OneDrive + pnpm symlinks:** Installing new packages under `apps/mobile/` can fail with `EPERM rename` because OneDrive locks files during sync. Pause OneDrive sync before running `pnpm add`. If a package still fails to resolve after install, run `pnpm install` from the repo root to repair the lockfile. Avoid packages requiring heavy native linking — `expo-image-picker`, `expo-image-manipulator`, and `react-native-pager-view` are fine (bundled in Expo Go).

**Metro cache after adding native modules:** When you add a native module (e.g. `react-native-pager-view`), Metro's transformer cache and module map don't always pick it up on a normal reload — you'll see `unable to resolve module …` even though the symlink exists in `apps/mobile/node_modules`. Restart with `pnpm expo start -c` (the `-c` clears the cache). Same fix applies whenever Metro's file watcher misses changes inside route groups like `(app)` on Windows + OneDrive.

**Package version drift (SDK 54):** If you see `expo-notifications@55.x` or any other wildly-wrong version in `apps/mobile/package.json`, run `pnpm expo install --check` from `apps/mobile` and accept all suggested fixes. SDK 54 expects `expo-notifications@~0.32.x`, `expo-image-picker@~17.x`, `expo-image-manipulator@~14.x`, etc. A mismatched `expo-notifications` will crash `(app)/_layout.tsx` at module-import time (the file calls `Notifications.setNotificationHandler` at the top), which manifests as the entire tab layout silently failing to render — the symptom looks like "tab bar disappeared" but is actually a JS exception you may not see in Metro unless you look closely.

**Testing with Expo Go:** Scan the QR code shown in the Metro terminal after running `pnpm dev:mobile`. Shake the device to get the reload menu. Press `r` in the Metro terminal to force reload. Expo Go is fine for JS/UI iteration, but push notifications and other native-module features require the EAS dev client (see **EAS dev-client builds** above). The mobile `dev` script is `expo start --go` (forces Expo Go) — because `expo-dev-client` is installed, plain `expo start` would default to dev-client mode and refuse to launch without a custom build. To deliberately run a dev client instead, use `expo start --dev-client` (the `start` script keeps the unflagged `expo start`).

**No web target — don't press `w`:** This Expo app is native-only. `react-native-web`, `react-dom`, and `@expo/metro-runtime` were removed as dependencies (and the `web` script + `app.json` web block were deleted) because `react-native-pager-view` ships no web implementation and never worked here. Pressing `w` in the Metro terminal (or running an old `pnpm web` from muscle memory) triggers a web bundle attempt that fails with `ERROR Importing native-only module "react-native/Libraries/Utilities/codegenNativeCommands"` — this is expected, not a regression. Use Expo Go on a real device/emulator (`a`/`i` in the terminal, or scan the QR code) instead.

### Session Phases

Sessions go through: `phase1` (proposal submission + thumbs up) → `phase2` (final yes/no votes) → `closed` → `archived`. There are no session subtypes anymore — every `Session` is a standard 2-phase live webapp session.

### Questions (Ja/Nej)

Single yes/no questions live in the `Question` collection (max 300 chars `text`), with votes in `QuestionVote` (ja/nej/abstar) and för/emot discussion in `QuestionComment` + `QuestionCommentRating`. Two origins: standalone questions created by admins for the mobile Hem/Rösta tabs, and questions spawned from a `MunicipalMeeting` agenda item on activation (these carry `meetingId`; the meeting's `items[].questionId` links back). **`deadline` is required** — questions are never subject to `Settings.sessionLimitHours`; they close when the deadline passes (daily cron) or when an admin closes them manually.

**Every vote is a BankID signature.** Both surfaces verify: the app via `POST /api/mobile/vote-verification`, the web via `POST /api/questions/vote-verification`. Both start a GrandID signing order over the ballot text, and both settle through the same `settleVerification()` (`lib/bankid/settle.ts`) — the only code that writes a verified vote. The signature also returns SPAR folkbokföring, checked for age (16+) and Vallentuna residency (kommunkod 0115) before the vote is recorded. See [docs/bankid-integration-plan.md](docs/bankid-integration-plan.md).

**The pre-election quota still applies (Fas 0).** Every user may cast at most **5 first-time** votes before the election on 2026-09-13; changing a vote already cast is free and consumes no slot. `PRE_ELECTION_LIMIT` and the shared helpers live in `lib/vote-quota.ts` — it is enforced on six paths (both verification start endpoints, `settleVerification`, the legacy mobile endpoint, and reported by the two list endpoints), which is too many copies of a number for it to be redeclared per file. Start endpoints check it so a doomed BankID signature is never paid for; **settle checks again, and that is the check that holds** — minutes pass while a voter signs, and another device could take the last slot. Known undercount: closing a question anonymises its votes by unsetting `userId`, so those stop counting toward the quota (accepted; see [docs/bankid-go-live-checklist.md](docs/bankid-go-live-checklist.md) §6).

**One person, one vote per question, across accounts.** Each verified vote carries `pnrHash` = `HMAC(VOTE_ID_PEPPER, personnummer + ":" + questionId)` under a unique partial index. Salting per question is what stops the hash doubling as a cross-question voting profile. **When a question closes its votes are anonymised** — `userId` and `pnrHash` unset, its `VoteVerification` rows deleted — so a closed tally is anonymous data and can no longer shift when someone deletes their account. See [docs/gdpr-data-retention.md](docs/gdpr-data-retention.md).

**Citizen-proposal quota (Fas 0):** Same pre-election restriction pattern as the voting quota above, but for medborgarförslag: a non-admin user may submit at most **1** citizen proposal before the election. Hardcoded `CITIZEN_PROPOSAL_LIMIT = 1` in `pages/api/mobile/citizen-proposals/index.ts`, counted via `CitizenProposal.countDocuments({ authorId })` (counts every proposal regardless of status, so a rejected/archived proposal still uses up the one slot — resubmission isn't allowed by tweaking status). Admins (`user.isAdmin` from the JWT) are exempt entirely, both for the POST gate and for the `canSubmit` flag. `GET /api/mobile/citizen-proposals` returns `canSubmit` so `proposals.tsx` can hide/relabel the submit button proactively instead of only failing on POST — necessary because a user's own rejected proposal doesn't appear in the (status-filtered) visible list, so the button can't be gated by "do I see one of my own in the list" alone.

## API Routes (70+)

### Auth

- `POST /api/auth/request-code` — Request OTP; if a valid code already exists for the email, returns `{ ok: true, alreadySent: true }` without resending (lets user proceed to code input). Creates and sends a new code only if none is active.
- `POST /api/auth/resend-code` — Invalidates the existing code and sends a fresh one. Enforces a 60-second server-side cooldown (returns `429` with `retryAfter` if called too soon).
- `/api/auth/[...nextauth]` — NextAuth handlers

### Sessions

- `GET /api/sessions/current` — Get active session + register user
- `GET /api/sessions/active` — Session info
- `GET /api/sessions/archived` — Archived list; top proposals ranked via a `ProposalRating` aggregation (no stored `averageRating`/`thumbsUpCount` anymore)
- `POST /api/sessions/advance-phase` — Admin: go to phase2
- `POST /api/sessions/execute-scheduled-transition` — Auto-transitions
- `POST /api/sessions/check-phase-transition`

### Proposals & Voting

- `GET/POST /api/proposals` — List / create proposals; GET computes `averageRating`/`ratingCount`/`commentsCount` at read time via aggregation (no denormalized fields); PATCH `action: "moveToFinalist"` sets `status: "finalist"` (renamed from `"moveToTop3"`/`"top3"`)
- `GET/POST /api/votes` — Get / submit final yes/no votes; auto-close now checks the session's own `deadline` field (replaces the old global `Settings.sessionLimitHours`)
- `POST /api/proposals/rate` — Rate proposal 1-5 (renamed from `/api/thumbsup`; backed by `ProposalRating`, no more denormalized write-back to `Proposal`)
- `GET /api/winning-proposals` — Winning proposals from the latest (or a given) closed session (renamed from `/api/top-proposals`; backed by `WinningProposal`)
- `GET/POST /api/comments` — List / create comments; rating computed at read time via `CommentRating` aggregation
- `POST /api/comments/rate` — Rate comment (no more write-back of `averageRating` onto `Comment`)

### Questions (Ja/Nej)

Single yes/no questions (mobile Hem/Rösta tabs, and questions spawned from municipal agenda items) live entirely outside `Session` now — see `Question`/`QuestionVote`/`QuestionComment`/`QuestionCommentRating` in the Database Schema section. Web-facing question management is admin-only, but voting itself is public on both surfaces: `/rosta` on the web and the Rösta tab in the app.

- `GET/POST /api/admin/questions` — List (with live ja/nej `voteCounts`) / create a standalone question (`meetingId` unset). POST requires `deadline`; sends an Expo push notification on creation
- `PATCH /api/admin/questions/[id]` — Edit text/deadline/imageUrl/categories (creator or superadmin only)
- `POST /api/admin/close-question` — Manually close a question (creator or superadmin only; municipal-spawned questions close via `/api/municipal/close-item` instead)
- `POST /api/admin/question-image` — Multipart image upload for a question; stores under prefix `question-images/`
- `GET /api/mobile/questions` — Returns `{ questions, quota }` (Bearer auth). Active first, then closed newest-first (capped at `CLOSED_QUESTION_LIMIT = 100` — closed questions are only reachable on Rösta, so the tail needn't be unbounded); each entry `{ id, text, imageUrl, isActive, deadline, categories, voteCounts, createdAt, userVote }`. `quota` is `{ used, limit }` (5-vote pre-election cap). `voteCounts` comes from a `$group` aggregation returning one row per question — **don't** go back to pulling every `QuestionVote` into the lambda and tallying in JS, which is what it used to do. The quota count is a `userId`-only predicate, which the `{questionId, userId}` compound index cannot serve (userId is not its prefix), so `QuestionVote.userId` carries its own standalone index — removing it silently reintroduces a collection scan on every request
- `POST /api/mobile/questions/vote` — ⚠️ **the unverified path, kept only for app builds already on phones.** Votes written here carry no `verifiedAt` and no `pnrHash`. Current builds use `/api/mobile/vote-verification` instead. Cannot be deleted until `MIN_SUPPORTED_MOBILE_VERSION` is raised in the same change
- `POST /api/mobile/vote-verification` — Start a BankID signing order for one ballot (`{ questionId, choice, returnUrl }`) → `{ verificationId, redirectUrl }`. The ballot is recorded before the voter sees BankID, so the choice cannot be swapped afterwards
- `GET /api/mobile/vote-verification/[id]` — Poll; settles and writes the vote the moment the signature completes. Scoped to the caller (another user's id → 404)
- `POST /api/mobile/vote-verification/[id]/cancel` — Release an abandoned order so the next attempt is not refused
- `GET/POST /api/mobile/questions/comments` — För/emot discussion (`?questionId=`); GET returns rating-sorted anonymized comments; POST requires the question to be active
- `POST /api/mobile/questions/comments/rate` — Upsert a 1-5 star rating on a question comment

### BankID login (both surfaces)

**BankID is the only way to create or open an account.** See [docs/bankid-login-plan.md](docs/bankid-login-plan.md).

- `POST /api/auth/bankid` — Start (web). `{ purpose: "login" | "link" }` → `{ pollToken, redirectUrl }`. **The only unauthenticated BankID endpoint**, so it is throttled on a hash of the caller's IP — every accepted order is billable
- `GET/DELETE /api/auth/bankid/[token]` — Poll (settles the login) / give up. A VERIFIED poll does **not** establish the session; the page then calls `signIn("bankid", { pollToken })`, and the `bankid` NextAuth provider spends the row exactly once
- `POST /api/mobile/auth/bankid` — Same, for the app
- `GET/DELETE /api/mobile/auth/bankid/[token]` — Poll; issues the JWT pair directly on VERIFIED (there is no NextAuth to hand off to), then answers `409 ALREADY_CONSUMED` to any later poll
- `GET /api/user/me` · `GET /api/mobile/user/me` — **No auth.** Capability, contact details and what membership still lacks. Both call `describeViewer()` so the surfaces cannot drift
- `POST /api/mobile/user/email` — Set or clear the account's **contact** address (empty string clears). Unverified, exactly like `/phone`: it stores a string and nothing else, and never merges. A taken address gets one of two 409s — `TAKEN` (another BankID account holds it, nothing to offer) or `MERGE_AVAILABLE` (a legacy account holds it, so the client offers the verified claim below). The partial unique index on `User.email` is what actually enforces it
- `POST /api/mobile/user/email/claim` — `{ action: "request" | "confirm", email?, code? }`. The **verified** half: a six-digit `MergeCode` to the address, then `confirm` folds the legacy account in (votes, proposals, membership) and attaches the address. Reached from the post-signup prompt and from the `MERGE_AVAILABLE` offer. Never returns a token

### Mobile Auth (JWT) — legacy, being retired

The OTP flow no longer creates accounts, and refuses any account that has BankID (C1). It survives only so a legacy email account can be signed into once, from an app build old enough to still offer the form, and reach the link gate. Deleted when `MIN_SUPPORTED_MOBILE_VERSION` rises.

- `POST /api/auth/request-code` — Request OTP. Silently declines to send to an unknown address or one belonging to a BankID account; the response is unchanged either way, so it still reveals nothing
- `POST /api/mobile/auth/verify-code` — Submit OTP. 404 if no such account, 403 `BANKID_ACCOUNT` if it uses BankID
- `POST /api/mobile/auth/refresh` — Exchange refresh token for new token pair

Access tokens: 7-day expiry · Refresh tokens: 30-day expiry · Signed with `NEXTAUTH_SECRET`

Mobile API calls pass `Authorization: Bearer <accessToken>`. Use `verifyBearerToken()` from `lib/mobile-jwt.ts` to protect mobile-specific routes.

### Other

- `GET /api/settings` — App settings (language/theme only — `sessionLimitHours` removed)
- `POST /api/settings` — Update settings (admin)
- `GET /api/user/activity`
- `POST /api/apply-admin`

- `POST /api/moderate` — Content moderation via Claude Haiku (uses `lib/ai.ts`)
- `POST /api/swish/callback` — **Unauthenticated by design** (Swish cannot present credentials). Three rules follow: (1) **never add `csrfProtection()`** — Swish has no way to get a token and every callback would 403; (2) the POST body is a _notification only_, never truth — we re-fetch the payment from Swish over mTLS and settle from that, so a forged POST cannot mark anything paid; (3) answer `200` for anything unactionable (unknown payment, malformed body) since Swish retries up to 10× until it gets a 200 and an unknown payment will never become known — most often it is a sandbox callback for a payment that exists only in a developer's local DB. A `callbackIdentifier` header that mismatches the stored value is rejected with `403`
- `POST /api/maj/review` — MAJ's create-time help (web, session-auth; `runMajReview()` in `lib/maj-review.ts`): writing tips + duplicate detection. Same shape/behavior as the mobile twin `/api/mobile/maj/review` (see Mobile Data). Consumed by `medborgarforslag.tsx` (förslag, with duplicates) and `rosta.tsx` `DebateSection` (argument, same-stance duplicates), both rendering `components/MajReviewSheet.tsx`
- `POST /api/csrf-token`
- `POST /api/payments/reconcile-swish` — Vercel Cron (daily 03:30, `apps/web/vercel.json`), Bearer `CRON_SECRET`. The safety net beneath the Swish callback and the app's polling: settles `CREATED` payments older than 10 min from an authoritative Swish `GET`, and marks ones Swish has never heard of after 24 h as `ERROR`/`UNKNOWN_AT_SWISH`. **Scoped to the deployment's own `SWISH_ENV`** — without that, a production run would look up sandbox payments against the production API, fail to find them, and wrongly abandon them. Batched to 100 per run
- `POST /api/check-session-timeout` — Vercel Cron (daily, `apps/web/vercel.json`), Bearer `CRON_SECRET`. Closes any active `Session` or `Question` whose own `deadline` has passed — both models carry their own deadline now, there is no global time limit to reintroduce.
- `POST /api/pusher/auth`
- `POST /api/unsubscribe`
- `DELETE /api/account/delete` — GDPR right-to-erasure. Deletes everything keyed to the user (proposals, comments, all six rating collections, votes incl. the `Question` family, citizen proposals + their blob images, budget votes/arguments, session requests, login codes), **severs** creator references rather than destroying shared content (`Session`/`Question`/`BudgetSession`/`MunicipalMeeting` `createdBy`, `closedBy`, `SessionRequest.processedBy`, and pulls the user out of `Session.activeUsers`), and **pseudonymises `Payment` instead of deleting it** — a paid membership fee is räkenskapsinformation under bokföringslagen (7 years) and GDPR art. 17.3 b exempts it, so `payerAlias`/`rawCallback` are cleared and `userDeletedAt` stamped. Requires an active NextAuth session. The invariant worth preserving: after deletion **no collection still contains that user's id** — when you add a model with a `ref: "User"` field, handle it here.

## Key Architecture Patterns

### Authentication Flow

Email → OTP code (bcrypt-hashed, 10min TTL) → NextAuth session → httpOnly cookie

### Anonymous browsing and the capability model

The whole app is **readable without an account**, on both surfaces. `"is there a
session?"` is no longer a sufficient question — a signed-in user can be exactly as
unable to act as an anonymous one — so every consumer route goes through
`lib/viewer.ts` instead:

| Capability     | Meaning                                             | May act |
| -------------- | --------------------------------------------------- | ------- |
| `anonymous`    | no account                                          | no      |
| `needs_bankid` | legacy email account, BankID not linked yet         | no      |
| `restricted`   | BankID-verified, not eligible to vote in Vallentuna | no      |
| `participant`  | BankID-verified and eligible                        | **yes** |

- `requireParticipant(req, res)` gates every write. Returns `401 ANONYMOUS` or
  `403 NEEDS_BANKID` / `403 RESTRICTED`.
- `requireAccount(req, res)` is the weaker gate for routes a blocked user still
  needs — their own membership, contact details, linking BankID. Linking must not
  sit behind `requireParticipant`, or `needs_bankid` would be inescapable.
- `optionalBearerToken()` replaces `verifyBearerToken()` on every mobile GET.
- **Capability is always read from the database, never from the token.** Access
  tokens live 7 days; a capability baked into one would leave someone who just
  linked BankID blocked for a week.
- `isAdmin` is orthogonal — admin surfaces gate on it alone, but an admin posting
  a comment goes through `requireParticipant` like anyone else.

Client side: web pages render read-only rather than redirecting to `/login`;
mobile has no auth guard on `(app)` and gates actions through `useActionGate()`
(`lib/RestrictedNotice.tsx`). Both surfaces mount a **link gate** that blocks a
`needs_bankid` account at startup, offering "link BankID" or "log out to
anonymous browsing" — the account is blocked, never the app.

### CSRF Protection

Dual-cookie pattern: readable cookie + httpOnly cookie. Hash-validated on all POST/PUT/DELETE. Frontend uses `fetchWithCsrf()` from `lib/fetch-with-csrf.ts`. Header: `x-csrf-token`.

### Database Connection

`connectDB()` in `lib/mongodb.ts` uses module-level caching to reuse connections across hot reloads and serverless invocations.

### Mongoose Model Cache (dev HMR gotcha)

`safeModel(name, schema)` returns the already-registered model if one exists — it never replaces it. This means schema changes are silently ignored during hot-module reloading, and Mongoose's strict mode will drop any new fields from documents. Models whose schemas change frequently must use the force-refresh pattern instead:

```ts
if (mongoose.models["ModelName"]) delete mongoose.models["ModelName"];
export const ModelName: AnyModel = mongoose.model("ModelName", ModelNameSchema);
```

`User`, `Settings`, `Session`, `CitizenProposal`, `MunicipalMeeting`, `BudgetSession`, `Question`, and `Payment` already use this pattern. Apply it to any model when adding or removing fields.

### Budget Median Algorithm

Collects all user allocations per category → computes median → balances total to match target budget. Nested support for subcategories.

### AI PDF Extraction

Claude API receives base64-encoded PDF. Budget extraction (`lib/budget/ai-extractor.ts`) produces categories + income sources + tax rates. Agenda extraction (`lib/municipal/agenda-extractor.ts`) produces meeting items.

### Real-time

- **Pusher:** All real-time fan-out (votes, phase transitions, ratings, new proposals, presence). Server publishes via `lib/pusher-broadcaster.ts`; clients subscribe via the `usePusher` hook. Presence channel `presence-active-users` powers the live "active users" count (authed through `POST /api/pusher/auth`).
- **Admin live panel:** uses `GET /api/admin/live-panel` polling (15s, paused while the tab is hidden) for proposal/vote progress metrics; Pusher events trigger immediate refetches but only when the event payload's `sessionId` matches the panel's session (`vote-update`/`rating-update` payloads carry `sessionId` for this). The panel is NOT rendered for `"voting"`-type sessions — its metrics (activeUsers, FinalVote counts, 75% conditions) don't apply to them and would poll forever showing zeros (with ~30 long-lived voting sessions this was ~6 req/s per admin tab and helped exhaust Atlas's connection limit). Voting-session cards instead show static Ja/Nej counts from `quickVoteCounts`, which `GET /api/admin/sessions` computes for active voting sessions via one `QuickVote` aggregation.

### Internationalization

5 languages: `sv` (default), `en`, `sr`, `es`, `de`. Translation files in `lib/locales/`. `useTranslation()` hook reads from `ConfigContext`.

### Theming

4 color schemes: `default` (blue/yellow), `green`, `red`, `blue`. CSS variables set dynamically. Managed via `ConfigContext`.

## Configuration Files

- **`turbo.json`** — Task pipeline: build depends on `^build`, dev is persistent + no cache; the build task declares **every** Vercel env var in `env[]`. Adding an env var to Vercel without adding it here is a silent bug: turbo hashes the declared set, so a changed value can serve a stale cached build. When you add an env var, add it to `env[]` in the same change. `$schema` is pinned to a versioned URL (`https://v2-10-11.turborepo.dev/schema.json`) by `@turbo/codemod update` — re-run that codemod when bumping turbo rather than editing the version by hand
- **`next.config.mjs`** — standalone output, transpiles all 36 D3 subpackages (ESM), optimizes lucide-react
- **`apps/web/tsconfig.json`** — target ES2018, lib es2018, path alias `@/*` → `./*`, strict OFF. Lib intentionally matches target so `tsc --noEmit` catches syntax newer than the target before build.
- **`postcss.config.mjs`** — Tailwind CSS v4 processing
- **`pnpm-workspace.yaml`** — `apps/*` + `packages/*`, plus the `allowBuilds` build-script allowlist for `sharp` and `unrs-resolver` (suppresses build-script warnings). This lived in root `package.json` as `pnpm.onlyBuiltDependencies` until the pnpm 11 upgrade moved it here
- **`package.json`** (root) — `packageManager` pins pnpm; `engines.node` is `>=22.13` because that's pnpm 11's floor
- **`.gitattributes`** — `* text=auto eol=lf` pins the working tree to LF. Prettier has no config in this repo, so `pnpm format` writes LF by its own default; git used to check files out as CRLF (`core.autocrlf=true` on Windows), so every format run rewrote all ~220 text files' line endings and left the entire repo showing as modified in `git status` while `git diff` showed nothing — real changes buried in phantom ones. Git already stored LF, so adding this changed no blob (`git add --renormalize .` was an empty diff); it only fixed what checkout writes to disk. Don't add an `endOfLine` setting to Prettier to work around this — the attributes file is the fix, and it applies to every developer regardless of their own `core.autocrlf`.
- **Formatting runs on commit, on staged files only.** `.husky/pre-commit` runs `pnpm exec lint-staged` (then `pnpm lint`), and the `lint-staged` block in the root `package.json` maps `*.{ts,tsx,js,jsx,mjs,cjs,md,json,yml,yaml,css}` to `prettier --write`. lint-staged re-stages what it rewrites, so the formatted version is what lands in the commit. Prefer this over putting `pnpm format` in the hook — the repo-wide script would pull unrelated files into every commit. Note that a Prettier upgrade can leave untouched files stale (Prettier 3 collapses short union types that older versions broke across lines), since the hook only ever sees files a commit touches; `pnpm format` is the way to sweep those up, and it is currently a no-op across the repo.
- **`apps/mobile/.eslintrc.js`** — extends `expo`; required so `eslint .` works without `expo lint` auto-installing packages. Deliberately has **no** react-hooks overrides — see below
- **React Compiler lint rules are enforced in `apps/web`, and absent in `apps/mobile`** — `eslint-plugin-react-hooks` 7.1 (pulled transitively by `eslint-config-next` 16.3) turns on `react-hooks/immutability` and `react-hooks/refs`. Both were demoted to warnings when the plugin landed; the underlying code has since been fixed and **both are now `"error"`** in `apps/web/eslint.config.mjs`. `next build` runs ESLint, so a regression fails the build — which is the point. The two patterns they catch: an effect calling a function declared textually below it (hoisting does **not** satisfy the rule — it works on lexical order, so move the declaration above the effect), and writing a ref during render (assign it in an effect instead; a render-phase ref write is unsafe under concurrent rendering).
- **`react-hooks/set-state-in-effect` stays a warning** with ~27 reports, all one shape: `useEffect(() => { fetchX() }, [...])` where `fetchX` is an async loader starting with `setLoading(true)`, so the rule sees a synchronous setState before the first `await`. That is the ordinary fetch-on-mount effect, not a defect, and the alternatives are all worse (drop the loading state, hide the call behind a microtask, or take on a data-fetching library). Don't mass-"fix" them. Do read a **new** report, though — the rule does find genuine derived-state misuse; it is how the write-only `userHasCreatedProposal` state in `session/[id].tsx` (a `useState` whose value was discarded, fed by an effect scanning every proposal) was found and deleted.
- **`no-unused-vars` is the `@typescript-eslint` version for `.ts`/`.tsx`** — scoped in a separate config block at the bottom of `apps/web/eslint.config.mjs`. The base rule reads the parameter names in a function _type_ annotation (`onRate: (id: string, rating: number) => void`) as unused bindings, which produced false positives that had been silenced with inline `eslint-disable` comments in `types/*.d.ts` and `lib/pusher-broadcaster.ts` (all since removed). The block is scoped to TypeScript because `eslint-config-next` only registers the plugin for TS files — applying the rule repo-wide makes ESLint fail outright on the remaining `.js` pages.
- **`apps/mobile` pins `eslint-plugin-react-hooks` ^5 as a direct devDependency.** It is on ESLint 8 + `eslint-config-expo` 10, which expects react-hooks ^5 — a version predating those rules. Two copies (5.2.0 and 7.1.1) exist in the workspace, and ESLint 8 resolves plugins relative to the **cwd**, not the config that declares them, so without the explicit dependency mobile would bind to whichever copy pnpm last exposed. That non-determinism is real: it flipped mid-session after an unrelated `pnpm add`, and mobile lint went from passing to 87 × "Definition for rule 'react-hooks/immutability' was not found". Never reference those rule names in `apps/mobile/.eslintrc.js`.
